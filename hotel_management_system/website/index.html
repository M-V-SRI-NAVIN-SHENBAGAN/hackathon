01 — Overview

What the project does

Abstract

Hotels lose money and time when bookings, guests, check-ins and payments live in paper registers: the same room gets allotted twice, bills are calculated by hand, and managers cannot say how much revenue was collected this month.

This project replaces that register with a normalized (3NF) PostgreSQL database — customer, room, reservation and payment — protected by primary keys, foreign keys, UNIQUE and CHECK constraints. A menu-driven Python application talks to it through psycopg2 using parameterized queries and explicit transactions.

Room availability is calculated date-wise, the bill is computed automatically as nights × room price, and check-in / check-out update the reservation and the room in one atomic transaction. Five views and 34 SQL queries produce all the management reports.

Problem statement

“Design and implement a database-backed Hotel Management System that stores customer, room, reservation and payment data in a normalized relational database, prevents duplicate bookings, calculates bills automatically, records check-in / check-out and payments, and produces management reports instantly.”

Objectives

  1. Design an ER model and a 3NF relational schema.
  2. Implement it in PostgreSQL with full integrity constraints.
  3. Build a simple menu-driven Python app using psycopg2.
  4. Calculate the total amount as nights × tariff.
  5. Prevent double booking with a date-overlap test.
  6. Keep reservation and room status consistent (transactions).
  7. Demonstrate every required SQL concept with real data.
  8. Document design, queries, screenshots and a demo script.

Design decisions

  • Surrogate primary keys (SERIAL) on every table
  • Bill stored, not recomputed later — tariff history
  • One payment row per reservation (UNIQUE)
  • Cancelled bookings do not block a room

02 — Database design

ER diagram, schema and normalization

Four entities, three relationships. The picture below is drawn from the same attribute list that sql/01_schema.sql creates, so the diagram cannot drift away from the database.

RESERVATION1 ⟶ 1PAYMENTone payment record per booking

Relational schema

Bold = primary key · FK = foreign key · UQ = unique constraint

Integrity constraints implemented

  • PRIMARY KEY on all four tables (SERIAL surrogates).
  • FOREIGN KEY reservation.customer_id → customer, reservation.room_id → room, payment.reservation_id → reservation.
  • ON DELETE rules: RESTRICT for booked customers/rooms (history kept), CASCADE for payments of a deleted reservation.
  • UNIQUE e-mail, phone, ID number, room number and one payment per reservation.
  • NOT NULL on every required column.
  • CHECK: check_out_date > check_in_date, price_per_night > 0, occupancy 1–6, valid room types, statuses and payment methods, 10-digit phone, booking date not after check-in.
  • Indexes on both foreign keys, on dates and on status columns.

Normalization — up to 3NF

1NF

Every column holds a single atomic value — no repeating groups, no comma-separated lists.

2NF

Each table has a single-column primary key, so no non-key attribute depends on only part of a key.

3NF

No transitive dependencies: tariffs live only in room, guest data only in customer, payment status only in payment.

An un-normalized booking sheet repeats the guest's phone for every booking and allows a room to exist only inside a booking. It is decomposed into four tables joined by foreign keys — a loss-less decomposition, because every table can be re-joined on its key. 

BOOKING (customer_name, customer_phone, customer_email, room_no,
         room_type, price, check_in, check_out, nights,
         total_amount, payment_method, payment_status)

   ↓ 3NF decomposition

customer(customer_id, ...)      room(room_id, ...)
reservation(reservation_id, customer_id→customer,
            room_id→room, ...)  payment(payment_id, reservation_id→reservation, ...)

How double booking is prevented

Two stays overlap when the existing check-in is before the wanted check-out and the existing check-out is after the wanted check-in. Only Booked and CheckedIn reservations block a room, so cancelling frees the dates automatically.

NOT EXISTS (
  SELECT 1 FROM reservation r
  WHERE r.room_id = rm.room_id
    AND r.status IN ('Booked', 'CheckedIn')
    AND r.check_in_date  < :wanted_check_out
    AND r.check_out_date > :wanted_check_in
)

Parameterized queries

db.query(
  "SELECT * FROM customer "
  "WHERE LOWER(full_name) LIKE LOWER(%s)",
  (f"%{keyword}%",))

User input never becomes SQL text → no SQL injection.

Atomic transactions

db.run_in_transaction([
  ("UPDATE reservation SET status="
   "'CheckedIn' WHERE reservation_id=%s", (id_,)),
  ("UPDATE room SET status='Occupied' "
   "WHERE room_id=%s", (room_id,)),
])

Check-in changes two tables — or neither.
