1. Abstract

Hotels still lose money and time because room bookings, guest records, check-ins, check-outs and payments are maintained in separate paper registers and spreadsheets. The same room gets allotted twice, the bill of a guest is calculated by hand, and management has no quick answer to questions such as "How much revenue did we collect this month?" or "Which room type is booked the most?"

This mini project, Hotel Management System, solves these problems with a small, complete, database-driven desktop application. All data is stored in a PostgreSQL relational database consisting of four normalized tables — customer, room, reservation and payment — protected by primary keys, foreign keys, NOT NULL, UNIQUE, CHECK constraints and referential-integrity rules. The front desk staff use a menu-driven Python application that talks to PostgreSQL through psycopg2 and performs real INSERT, SELECT, UPDATE and DELETE operations using parameterized queries.

The system covers six functional modules: customer management, room management, reservation management, check-in/check-out, payment management and reports. Room availability is calculated date-wise from the reservation table, the booking amount is computed automatically as number of nights × room price, and check-in/check-out update the reservation and the room in one atomic transaction. Five SQL views and thirty-four demonstration queries (joins, subqueries, aggregates, GROUP BY, HAVING, ORDER BY) provide the reports needed by the management.

The result is a working, easy-to-understand mini project in which the ER diagram, the relational schema, the SQL scripts and the Python code all describe exactly the same database.

Keywords: hotel management, relational database, PostgreSQL, psycopg2, normalization, ER model, constraints, transactions.

2. Problem statement

A small hotel (about 10–30 rooms) records everything manually:

  • Guest details are written in a register. Searching an old guest means turning pages for several minutes.
  • Room allotment is decided by looking at a whiteboard, so the same room is sometimes given to two guests for overlapping dates.
  • The bill is calculated by hand, so arithmetic mistakes happen and the amount is sometimes not recorded against the guest at all.
  • Payment details (cash / card / UPI) are kept in a separate cash book, so the reception cannot say whether a guest has paid.
  • At the end of the month the manager has to add up pages of the register to find the revenue or the most popular room type.

Problem statement: Design and implement a database-backed Hotel Management System that stores customer, room, reservation and payment data in a normalized relational database, prevents duplicate bookings, calculates bills automatically, records check-in/check-out and payments, and produces the management reports instantly — while remaining simple enough to be understood and demonstrated by a second-year CSE student.

3. Objectives

  1. Design an ER model and a normalized (up to 3NF) relational schema for a hotel front-desk system.
  2. Implement the schema in PostgreSQL with all necessary integrity constraints (PRIMARY KEY, FOREIGN KEY, NOT NULL, UNIQUE, CHECK, ON DELETE rules).
  3. Build a beginner-friendly, menu-driven Python application using psycopg2 that performs real database operations for every module.
  4. Automate the calculation of the total booking amount (nights × price per night).
  5. Prevent double booking by checking date-wise room availability before a reservation is stored.
  6. Record check-in, check-out and payments, keeping the reservation status and room status consistent in a single transaction.
  7. Demonstrate the SQL concepts required by the syllabus — CREATE TABLE, INSERT, UPDATE, DELETE, SELECT … WHERE, ORDER BY, aggregate functions, GROUP BY, HAVING, INNER JOIN, LEFT JOIN, subqueries and views — with realistic sample data and their actual output.
  8. Produce complete documentation: ER diagram, relational schema, normalization notes, screenshots and a demonstration script.

Advantages of the proposed system

  • Single source of truth — one PostgreSQL database for all modules.
  • Data integrity enforced by the DBMS, not only by the program.
  • Availability and revenue reports are produced in milliseconds.
  • The application uses parameterized queries, so SQL injection is avoided.
  • Check-in / check-out are atomic: the reservation and the room can never disagree.

6. Description of functional modules

The application has a main menu with six functional modules. Each module has its own sub-menu and calls the functions of one Python file.

6.1 Customer management (app/customers.py)

Operation SQL used
Add a customer INSERT INTO customer … RETURNING customer_id
View all customers SELECT … ORDER BY customer_id
Search by ID / name / phone SELECT … WHERE customer_id = %s OR phone = %s OR LOWER(full_name) LIKE %s
Update details UPDATE customer SET … WHERE customer_id = %s
Delete a customer DELETE FROM customer WHERE customer_id = %s

The program validates the e-mail format, the 10-digit phone number and the ID-proof type before contacting the database. A customer who already has reservations cannot be deleted — the foreign key from reservation (ON DELETE RESTRICT) protects referential integrity, and the program explains this to the user instead of showing an SQL error.

6.2 Room management (app/rooms.py)

  • Add a room (room number, category, floor, price per night, maximum guests, initial status).
  • Display all rooms and the tariff of every category (with GROUP BY).
  • Display currently available rooms.
  • Update a room's details or status (Available, Occupied, Maintenance). A room with a checked-in guest cannot be set to Available.
  • Availability for a date range is computed in the reservation module by looking for overlapping reservations — this is the correct way, because a room can be sold today and free next week.

6.3 Reservation management (app/reservations.py)

  • Book a room: choose the customer (search by name/phone/ID), choose check-in and check-out dates and the number of guests, then the system lists only the rooms that are free for those dates and can hold the party.
  • Availability check: NOT EXISTS sub-query over reservation with the overlap test existing.check_in < wanted.check_out AND existing.check_out > wanted.check_in, ignoring cancelled bookings and rooms under maintenance.
  • Bill calculation: total_amount = (check_out − check_in) × price_per_night, shown to the user for confirmation before saving.
  • A payment row with status Pending is inserted in the same flow, so the payment module always has a record to work on.
  • View all reservations (filtered by status or customer), view one reservation with its payment, and cancel a reservation (only a Booked reservation can be cancelled; a refundable amount is marked Refunded).

6.4 Check-in and check-out management (app/frontdesk.py)

Operation Reservation status Room status
Check-in Booked → CheckedIn, actual_check_in set Available → Occupied
Check-out CheckedIn → CheckedOut, actual_check_out set Occupied → Available

Both statements are executed inside one transaction (db.run_in_transaction). If the second UPDATE fails, the first is rolled back, so the database can never end up with a guest inside a "free" room. The module also lists today's expected arrivals and departures, and offers to collect the payment during check-out.

6.5 Payment management (app/payments.py)

  • Record a payment against a reservation (method Cash / Card / UPI, optional transaction reference).
  • Change the payment status from Pending to Paid, or mark a paid amount as Refunded.
  • Display payment details, including a filter for pending payments and the outstanding amount.

6.6 Reports and search (app/reports.py)

  1. All reservations (with customer, room, payment status).
  2. Currently occupied rooms and the guests staying in them (occupancy %).
  3. Rooms available right now.
  4. Customer booking history (bookings, completed stays, cancellations, money spent) — all customers or one selected customer.
  5. Total hotel revenue — overall, by payment method and by month, plus the pending and refunded amounts.
  6. Most frequently booked room type.
  7. Room-status / occupancy summary and per-room-type performance.
  8. Search reservations by customer, by date or by status.

9.1 Key identification

Table Primary key Foreign keys Other important constraints
customer customer_id — email, phone, id_proof_number are UNIQUE
room room_id — room_number is UNIQUE; CHECK on type, price, occupancy
reservation reservation_id customer_id, room_id CHECK (check_out_date > check_in_date)

9.2 Referential integrity rules

Foreign key On update On delete Why
reservation.customer_id CASCADE RESTRICT A customer with bookings must not be deleted; their history stays intact.
reservation.room_id CASCADE RESTRICT A booked room cannot be removed from the hotel.
payment.reservation_id CASCADE CASCADE If a reservation is removed, its payment record is meaningless and is removed with it.

The application additionally checks these rules and prints a friendly message before the database has to reject anything.

10. Normalization

Normalization removes redundancy and update anomalies. The design below is in third normal form (3NF).

10.1 First Normal Form (1NF) — atomic values only

Every column of every table stores a single, indivisible value: no repeating groups, no comma-separated lists and no multiple phone numbers in one column. If a guest had two phone numbers, a separate row (a new guest record) would be needed rather than "98400…, 98401…" in one cell.

10.2 Second Normal Form (2NF) — no partial dependency

2NF applies to tables with composite primary keys. In this design each table has a single-column surrogate key (customer_id, room_id, reservation_id, payment_id), so every non-key attribute depends on the whole key — there is no partial dependency. Example: in reservation, total_amount depends on check_in_date, check_out_date and room_id, all of which are attributes of the same reservation row.

10.3 Third Normal Form (3NF) — no transitive dependency

No non-key column depends on another non-key column:

  • price_per_night is stored once, in room, not copied into every reservation; reservation.total_amount is a derived, stored historical value (the price at the time of booking, needed for old bills) and not a copy of a mutable attribute.
  • A room's category, floor and tariff are all properties of the room alone, so they live in room, not in reservation.
  • The guest's name, phone and e-mail live only in customer; payment contains only payment data and a reference to the reservation, instead of repeating the customer's name.
  • payment_status belongs to payment, status belongs to reservation; they are never duplicated in another table.

10.4 Decomposition example

An un-normalized booking sheet would look like:

BOOKING (customer_name, customer_phone, customer_email, room_no, room_type,
         price, check_in, check_out, nights, total_amount, payment_method,
         payment_status)

Problems: the same customer's phone is typed again for every booking (update anomaly), a new room cannot be recorded without a booking (insert anomaly), and deleting the last booking of a customer erases the customer (delete anomaly).

Decomposition:

New table Attributes kept
customer customer_id, full_name, email, phone, address, ID proof
room room_id, room_number, room_type, floor_no, price_per_night, max_occupancy, status
reservation reservation_id, customer_id, room_id, dates, num_guests, total_amount, status
payment payment_id, reservation_id, amount, method, status, date

Each relationship that was inside BOOKING is now represented by a foreign key, and the decomposition is loss-less because every table can be re-joined on its primary key.

10.5 Why not a separate room_type table?

A room_type(room_type_id, category, default_price) table would be "more normalized", but the category list is fixed by a CHECK constraint and the tariff differs per room (room 111 costs 4200 while room 105 costs 4000), so a separate table would add a join without removing any redundancy. For a college mini-project the simpler four-table design is correct and still 3NF.

11. SQL commands and queries

All statements are in sql/ and were executed on PostgreSQL 16. The complete output of every query is produced by running psql -d hotel_db -f sql/03_queries.sql.

11.1 CREATE TABLE (excerpt — full script in sql/01_schema.sql)

CREATE TABLE reservation (
    reservation_id    SERIAL        PRIMARY KEY,
    customer_id       INTEGER       NOT NULL,
    room_id           INTEGER       NOT NULL,
    check_in_date     DATE          NOT NULL,
    check_out_date    DATE          NOT NULL,
    booking_date      DATE          NOT NULL DEFAULT CURRENT_DATE,
    num_guests        INTEGER       NOT NULL CHECK (num_guests BETWEEN 1 AND 6),
    total_amount      NUMERIC(10,2) NOT NULL CHECK (total_amount >= 0),
    status            VARCHAR(20)   NOT NULL DEFAULT 'Booked'
                      CHECK (status IN ('Booked','CheckedIn','CheckedOut','Cancelled')),
    actual_check_in   TIMESTAMP,
    actual_check_out  TIMESTAMP,

    CONSTRAINT fk_reservation_customer
        FOREIGN KEY (customer_id) REFERENCES customer (customer_id)
        ON UPDATE CASCADE ON DELETE RESTRICT,
    CONSTRAINT fk_reservation_room
        FOREIGN KEY (room_id) REFERENCES room (room_id)
        ON UPDATE CASCADE ON DELETE RESTRICT,
    CONSTRAINT chk_reservation_dates
        CHECK (check_out_date > check_in_date),
    CONSTRAINT chk_reservation_booking_date
        CHECK (booking_date <= check_in_date)
);

-- Q20: LEFT JOIN keeps customers who never booked
SELECT c.customer_id, c.full_name,
       COUNT(r.reservation_id) AS bookings,
       COALESCE(SUM(r.total_amount), 0) AS booking_value
FROM customer c
LEFT JOIN reservation r ON r.customer_id = c.customer_id
GROUP BY c.customer_id, c.full_name
ORDER BY bookings DESC, c.customer_id;

-- Q21: LEFT JOIN room -> reservation shows the never-booked room
SELECT rm.room_id, rm.room_number, rm.room_type,
       COUNT(r.reservation_id) FILTER (WHERE r.status <> 'Cancelled')
                                 AS confirmed_bookings
FROM room rm
LEFT JOIN reservation r ON r.room_id = rm.room_id
GROUP BY rm.room_id, rm.room_number, rm.room_type
ORDER BY rm.room_id;

Room 110 (Double, under maintenance) appears with 0 bookings, which an INNER JOIN would have hidden.

11.6 Subqueries

-- Q24: scalar subquery — rooms above the average price
SELECT room_number, room_type, price_per_night
FROM room
WHERE price_per_night > (SELECT AVG(price_per_night) FROM room)
ORDER BY price_per_night;

-- Q23: NOT EXISTS — rooms never booked
SELECT room_number, room_type, status
FROM room rm
WHERE NOT EXISTS (SELECT 1 FROM reservation r WHERE r.room_id = rm.room_id);

-- Q26: derived table — the most frequently booked room type
SELECT room_type, times_booked
FROM (SELECT rm.room_type, COUNT(*) AS times_booked
      FROM reservation r
      INNER JOIN room rm ON rm.room_id = r.room_id
      WHERE r.status <> 'Cancelled'
      GROUP BY rm.room_type) AS booking_counts
ORDER BY times_booked DESC, room_type
LIMIT 1;

-- Q25: correlated subquery — customers above the average booking value
SELECT c.customer_id, c.full_name, SUM(r.total_amount) AS total_booking_value
FROM customer c
INNER JOIN reservation r ON r.customer_id = c.customer_id
GROUP BY c.customer_id, c.full_name
HAVING SUM(r.total_amount) > (SELECT AVG(total_amount) FROM reservation)
ORDER BY total_booking_value DESC;

11.7 Date-wise availability query

-- Q27: rooms free between two dates (the heart of the booking module)
SELECT rm.room_id, rm.room_number, rm.room_type, rm.price_per_night
FROM room rm
WHERE rm.status <> 'Maintenance'
  AND NOT EXISTS (
        SELECT 1
        FROM reservation r
        WHERE r.room_id = rm.room_id
          AND r.status IN ('Booked', 'CheckedIn')
          AND r.check_in_date  < DATE '2026-12-03'     -- wanted check-out
          AND r.check_out_date > DATE '2026-12-01'     -- wanted check-in
      )
ORDER BY rm.price_per_night;

Two stays overlap when the existing check-in is before the wanted check-out and the existing check-out is after the wanted check-in. Cancelled reservations are ignored, so cancelling a booking frees the room automatically.

11.8 Views

CREATE VIEW vw_reservation_details AS
SELECT r.reservation_id, c.customer_id, c.full_name AS customer_name,
       c.phone AS customer_phone, rm.room_number, rm.room_type,
       rm.price_per_night, r.check_in_date, r.check_out_date,
       fn_stay_nights(r.check_in_date, r.check_out_date) AS nights,
       r.num_guests, r.total_amount, r.status,
       COALESCE(p.payment_status, 'Not Paid') AS payment_status
FROM reservation r
INNER JOIN customer c ON c.customer_id = r.customer_id
INNER JOIN room     rm ON rm.room_id   = r.room_id

12. Application

The application is a menu-driven Python program that connects to PostgreSQL and performs all hotel management operations. It consists of six functional modules and handles booking, availability, billing logic, and visitor actions.

What it does:

  • Customer management — add, list, search, update and delete guests.
  • Room management — add rooms, list all rooms, show tariff/occupancy, update status.
  • Reservation management — book a room, check availability, view and cancel reservations.
  • Check-in / check-out — record guest arrival and departure in one transaction.
  • Payment management — record Cash / Card / UPI payments and refunds.
  • Reports and search — eight reports built with joins, aggregates, views and subqueries.

Six modules:

  1. Customer management (customers.py)
  2. Room management (rooms.py)
  3. Reservation management (reservations.py)
  4. Check-in / check-out (frontdesk.py)
  5. Payment management (payments.py)
  6. Reports and search (reports.py)

Booking / availability / billing logic:

  • Date-wise availability is checked before a reservation is stored.
  • Total amount is computed automatically as nights × room price.
  • Check-in / check-out updates the reservation and the room in one atomic transaction.

Visitor actions:

  • Search customers by name, phone or ID.
  • Book a room after an availability check.
  • Record check-in and check-out.
  • Record payments (Cash / Card / UPI) or refunds.
  • Run the eight management reports instantly.

14. Results and observations

14.1 Results

  • All four tables, five views, indexes and the helper function were created successfully in PostgreSQL 16 (sql/01_schema.sql).
  • The sample database contains 12 customers, 14 rooms (Single, Double, Deluxe, Suite), 16 reservations (Booked, CheckedIn, CheckedOut, Cancelled) and 16 payments (Cash, Card, UPI; Pending, Paid, Refunded).
  • Total revenue in the sample data is ₹1,01,100.00 from 9 paid transactions; pending amount ₹83,000 and refunded amount ₹3,200 are reported separately.
  • All 34 demonstration queries run without errors and produce the output documented in section 11.
  • Every module of the Python application was executed against the real database: customer add/search/update/delete, room add/update, booking with availability check and automatic billing, check-in, check-out, payment recording, refund and all eight reports.
  • Integrity rules were verified by deliberately trying to break them: a duplicate e-mail, an invalid ID-proof type, a two-character name, a check-out date before the check-in date, a room booked twice for the same dates and deleting a customer who has reservations — each attempt was rejected with a clear message.

14.2 Observations

  1. Constraints are the real safety net. The application validates input, but a UNIQUE or CHECK constraint also protects the data when somebody edits the tables directly with psql or pgAdmin.
  2. Availability must be date-based. Using only room.status would let a room be booked twice for future dates; the NOT EXISTS overlap query is the correct approach and is also fast because of idx_reservation_dates.
  3. Transactions matter. Check-in and check-out change two tables. Without a transaction, a failure between the two UPDATEs would leave a guest in a "free" room.
  4. Views simplify the Python code. vw_reservation_details removed the need to repeat a three-table join in six different screens.
  5. Storing the bill amount is deliberate. reservation.total_amount is kept even though it can be recalculated, because the tariff of a room can change later and old bills must not change.
  6. Small usability details matter: showing the bill before saving, offering to collect payment at check-out, and printing the outstanding amount in the pending-payments report make the program pleasant to use.

14.3 Limitations and future scope

  • One payment per reservation (partial payments are not supported).
  • No login/authentication — the menu is meant for a single front-desk terminal.
  • Availability is checked when the booking is saved, but there is no database-level EXCLUDE constraint against two overlapping bookings inserted at exactly the same moment (a single-user mini project does not need it; it is mentioned as future work).
  • Possible extensions: a Tkinter GUI, invoice printing/PDF, e-mail confirmation, housekeeping module, GST calculation, and a room_type master table with seasonal pricing.

15. Conclusion

A complete, working Hotel Management System was designed, implemented and tested. The database is a normalized (3NF) PostgreSQL schema of four related tables with primary keys, foreign keys, UNIQUE, NOT NULL and CHECK constraints, five views and an availability query based on date overlap. The Python application connects through psycopg2 and offers a simple menu-driven interface for customers, rooms, reservations, check-in, check-out, payments and reports, using parameterized SQL and transactions.

The ER diagram, the relational schema, the SQL scripts and the Python code all describe the same four entities and the same relationships, and every required SQL concept — from CREATE TABLE to GROUP BY … HAVING, joins, subqueries and views — is demonstrated with realistic data and actual output.

The project therefore fulfils the objectives of the Database Systems mini project: it shows database design, integrity enforcement, SQL skills and a functional application that interacts with the database, while remaining simple enough to be explained and extended in a viva.

Appendix A — How to create the database and run the project

Step 1 — Install the software

  • Install PostgreSQL (remember the password you set for the postgres user) and make sure the service is running.
  • Install Python 3.10+ and the driver:

bash pip install psycopg2-binary

Step 2 — Create the database

From the hotel_management_system folder:

psql -U postgres -f sql/00_create_database.sql

This creates the database hotel_db and connects to it.

Step 3 — Create the tables and load the sample data

psql -U postgres -d hotel_db -f sql/01_schema.sql
psql -U postgres -d hotel_db -f sql/02_sample_data.sql

01_schema.sql can be re-run safely (it drops and recreates the objects). 02_sample_data.sql restarts the IDs and reloads the 12 + 14 + 16 + 16 sample rows.

Step 4 — Demonstrate the SQL queries (optional)

psql -U postgres -d hotel_db -f sql/03_queries.sql

Step 5 — Configure the connection

cp .env.example .env      # Windows: copy .env.example .env

Edit .env and put your own PostgreSQL password.

Step 6 — Run the application

cd app
python main.py

The main menu appears. Type the number of a module and press ENTER.

Note (Windows): if py is the Python launcher on your system use py main.py; if psql is not on PATH, use the full path such as "C:\Program Files\PostgreSQL\16\bin\psql.exe".
